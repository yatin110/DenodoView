# STAGE 7 OBJECTIVE

Implement Vue Pilot's first real governed enterprise tool integration:

# DENODO

The objective is to make Denodo metadata and approved Denodo data capabilities available to the Stage 6 orchestration layer through a controlled integration.

The architecture should conceptually remain:

User
↓
Vue Pilot Chat
↓
Chat Orchestrator
↓
Tool Registry
↓
Denodo Tool Provider
↓
Denodo Integration Layer
↓
MCP / Denodo-approved interface
↓
Denodo

The AI must NOT connect directly to Denodo.

Frontend code must NOT connect directly to Denodo.

All Denodo activity must pass through controlled backend services.

---

# 1. DISCOVER THE ACTUAL DENODO INTEGRATION AVAILABLE

Before implementing adapters, inspect the repository/environment and determine what Denodo integration mechanism is actually available.

Potential possibilities may include:

* an MCP server exposing Denodo capabilities,
* an existing internal API,
* VDP/REST integration,
* another approved service abstraction.

Do NOT invent tools or endpoints.

If MCP is configured, inspect the actual MCP tool definitions available.

Create adapters only around real capabilities.

Document internally which tools/capabilities were discovered.

If some desired capability does not exist, do not simulate it.

Build the architecture so it can be added later.

---

# 2. DENODO TOOL PROVIDER

Implement a Denodo-specific tool provider compatible with the generic Stage 6 tool-provider interface.

Conceptually:

DenodoToolProvider

should expose approved Denodo-related capabilities to the central ToolRegistry.

The provider should:

* register Denodo tools,
* expose tool descriptions,
* expose validated input schemas,
* map generic Vue Pilot tool calls to real Denodo/MCP operations,
* normalise responses into Vue Pilot ToolResult objects,
* apply timeouts,
* handle Denodo/provider failures,
* enforce read-only restrictions,
* attach useful operational metadata.

Do NOT place orchestration logic inside the provider.

The Denodo provider executes approved operations.

The orchestrator decides when those operations are required.

---

# 3. CAPABILITY CATEGORIES

Where supported by the real Denodo interface, organise capabilities into meaningful categories.

Potential categories include:

## Discovery

* list/search databases or virtual databases
* search views
* find views by name
* find views by keyword or description

## Metadata

* get view metadata
* get fields/columns
* data types
* descriptions
* keys where available
* source information where exposed
* tags/categories if supported

## Lineage

* upstream dependencies
* downstream dependencies
* source lineage
* field-level lineage if supported by the actual interface

## Query support

* construct or validate read-only VQL/query requests
* execute governed read-only queries
* retrieve limited result sets

Only implement capabilities that really exist in the current environment.

Do not create fictional Denodo MCP methods.

# 5. METADATA-FIRST WORKFLOW

Implement and reinforce metadata-first behaviour.

For questions involving data, the orchestrator should have the capabilities required to follow a flow similar to:

User question
↓
Discover candidate Denodo views
↓
Inspect relevant view metadata
↓
Inspect fields
↓
Inspect relationships/lineage when needed
↓
Determine whether enough information exists
↓
Construct a safe query if data retrieval is necessary
↓
Validate query where possible
↓
Execute approved read-only query
↓
Analyse returned data
↓
Answer

Do not make "generate SQL/VQL immediately" the default behaviour.

Metadata should guide query generation.

---

# 10. READ-ONLY QUERY EXECUTION

If the real integration supports querying data, implement a heavily controlled read-only execution path.

Important requirements:

* SELECT/read-only behaviour only.
* No INSERT.
* No UPDATE.
* No DELETE.
* No DROP.
* No ALTER.
* No CREATE.
* No arbitrary admin commands.
* No multi-statement execution unless explicitly approved by the existing architecture.
* Enforce maximum row count.
* Enforce timeout.
* Enforce maximum result payload.
* Validate supplied query before execution where practical.
* Reject clearly unsafe queries before sending them to Denodo.

Do not rely solely on the LLM to produce safe VQL.

Safety belongs in deterministic application logic.

---

# 11. QUERY LIMITS

Introduce configuration for:

* default result row limit,
* absolute maximum row limit,
* query timeout,
* metadata result limits,
* maximum payload size,
* maximum number of candidate views returned.

Do not hard-code arbitrary production values throughout the code.

Use central configuration.

---

# 12. QUERY VALIDATION

Where supported, add validation before execution.

Validation should check, at minimum:

* operation appears read-only,
* query length is reasonable,
* forbidden operations are absent,
* requested row limit is within policy.

If Denodo exposes a real validation/explain capability, wrap it appropriately.

Do not claim a query has been validated by Denodo unless that operation actually occurred.

---

# 13. RESULT NORMALISATION

Normalise query results before returning them to the orchestrator.

The orchestrator should receive predictable structures rather than provider-specific response objects.

Handle:

* columns,
* rows,
* row count,
* truncation,
* nulls,
* types where available,
* provider warnings,
* timeout/error information.

If results were truncated, expose that explicitly so the final answer does not imply completeness.

---

# 14. LARGE RESULT SET HANDLING

Do not send massive Denodo result sets directly into the LLM context.

Implement safeguards.

Possible strategies:

* hard row limits,
* server-side aggregation,
* result summarisation,
* selecting only required columns,
* returning schema plus sample,
* returning aggregate results rather than raw rows.

For this stage, prioritise hard limits and sensible structured outputs.

Do not over-engineer a large-data analytics engine yet.

---

# 15. USER ACCESS / GOVERNANCE

Preserve the authenticated user's context.

If the Denodo integration supports per-user permissions or delegated identity, use the existing architecture accordingly.

If access uses a service identity, Vue Pilot must still enforce application-level governance and never imply that the user's Denodo permissions have been checked if they have not.

Do not allow the AI to select or override an arbitrary user identity.

Credentials must come from secure application configuration or approved identity flow.
