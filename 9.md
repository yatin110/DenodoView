# STAGE 9 OBJECTIVE

Implement a robust **context-management and knowledge-handling layer** for Vue Pilot.

The goal is to ensure that every AI request receives:

* the right context,
* only the context it actually needs,
* context from the appropriate sources,
* context within safe size/token limits,
* clearly distinguishable evidence/source information,
* enough conversational history to understand follow-up questions,
* without continuously sending the entire conversation, tool history, metadata catalogue or documentation corpus to the model.

Vue Pilot should progressively become capable of understanding:

* the current user's question,
* relevant previous turns in the current conversation,
* previously referenced Denodo objects,
* relevant tool results,
* business/application knowledge,
* technical documentation,
* project-specific instructions,
* source/provider provenance,

while staying efficient and accurate.

This stage should NOT create another orchestration framework.

It must extend the context-building architecture created in Stage 6 and work with the multi-provider framework created in Stage 8.

# 3. CONTEXT TYPES

Represent context using typed structures rather than one giant string.

Conceptually support categories such as:

## Core instructions

Permanent Vue Pilot behaviour and operating rules.

## User request

The current user question.

## Conversation context

Relevant prior user/assistant turns.

## Entity/object context

Previously referenced Denodo views, fields, schemas, documents or objects.

## Knowledge context

Relevant documentation or business/technical knowledge retrieved from approved providers.

## Tool evidence

Results produced during the current orchestration run.

## Source/provenance context

Information identifying where evidence came from.

## Runtime context

Safe request-level information needed by orchestration.

Do not expose secret execution context to the model.

---

# 4. CONVERSATION WINDOW MANAGEMENT

Do NOT blindly send the entire conversation history to the model.

Implement configurable limits.

Use a strategy such as:

* always include the current user question,
* include the most recent relevant conversation turns,
* preserve important referenced entities,
* preserve recent unresolved questions,
* exclude unnecessary old chatter,
* stay within configured context/token budgets.

Initially, recent-turn selection is acceptable.

Design the interface so semantic relevance or summarisation can be introduced later.

---

# 5. FOLLOW-UP QUESTION RESOLUTION

Vue Pilot must handle contextual follow-ups.

Examples:

User:
"Find views related to counterparty exposure."

Assistant returns three views.

User:
"Show me the fields in the second one."

Vue Pilot should understand what "the second one" refers to.

Another example:

User:
"Explain CUSTOMER_RISK."

Later:

"Where does its exposure field come from?"

The system should retain enough structured conversation/object context to resolve "its".

Do not depend solely on textual history where structured references can help.

---

# 6. CONVERSATION ENTITY MEMORY

Introduce the concept of structured entities referenced during the conversation.

Examples:

* Denodo database
* Denodo view
* field/column
* lineage object

* query/result identifier

Conceptually:

ConversationEntity {

displayName

}

# 7. REQUEST-SCOPED CONTEXT VS DURABLE CONTEXT

Clearly separate:

## Request-scoped context

Temporary information used during one orchestration run.

Examples:

* intermediate tool outputs,
* candidate objects,
* current query result,
* orchestration step data.

## Durable conversation context

Information useful across later messages.

Examples:

* conversation summary,
* identified object references,
* previous user/assistant messages,
* safe structured references.

Do not persist every intermediate tool payload simply because it was used by the agent.

---

# 8. TOOL RESULT CONTEXT MANAGEMENT

Large tool results must not automatically be inserted verbatim into model context.

Implement a context transformation layer.

For example:

Denodo returns:

* 500 rows
* 80 columns

Do NOT automatically send all 500 × 80 values to the LLM.

Instead support controlled representations such as:

* schema,
* selected relevant fields,
* row count,
* truncated samples,
* aggregates,
* filtered subset,
* lightweight summary,
* source metadata.

Tool providers should still preserve raw execution result where required by the backend, but model context should receive only the appropriate representation.

# 9. CONTEXT BUDGET

Introduce a configurable context budget.

The implementation should consider:

* model context window,
* requested output budget,
* tool definitions,
* core instructions,
* conversation history,
* retrieved evidence,
* current user question.

Do not hard-code model-specific magic numbers throughout the code.

Create a central configuration/policy.

Conceptually:

TOTAL_MODEL_BUDGET

minus:

* response reserve
* system instructions
* tool definitions

remaining:

* conversation
* knowledge
* evidence

Exact token calculation may depend on the existing model provider.

Use the provider's supported token-counting mechanism if available.

If exact counting is unavailable, use a documented approximation.

---

# 10. PRIORITY-BASED CONTEXT SELECTION

Not all context has equal importance.

Define a sensible priority order.

For example:

Highest priority:

* current user question
* core instructions
* critical safety/governance instructions

Then:

* directly relevant recent conversation turns
* current tool evidence
* directly referenced object metadata

Then:

* supporting knowledge/documentation
* older conversation history

Lowest:

* unrelated old conversation content
* verbose raw tool outputs

The exact implementation may be weighted/scored or rule-based.

Keep it understandable and testable.

# 16. HYBRID CONTEXT

Vue Pilot should be able to combine:

* Denodo metadata
* Denodo query results
* documentation/knowledge
* conversation history

2. Knowledge provider finds business definition.
3. ContextBuilder selects relevant evidence.

# 19. CONVERSATION SUMMARY

Implement the abstraction needed for long-running conversation summaries.

For conversations that become too long, the system should be able to maintain a compact summary containing:

* important user objectives,
* previously established facts,
* referenced objects,
* unresolved questions,
* key decisions/results.

Do not store chain-of-thought.

Do not store hidden model reasoning.

For this stage, one of these approaches is acceptable:

A. implement actual summarisation when thresholds are exceeded,

or

B. implement the service/interface plus a conservative initial deterministic summary approach.

Prefer actual implementation if the existing model/provider architecture makes it straightforward.

---

# 20. SUMMARY SAFETY

Conversation summaries must not silently become authoritative facts.

They are compressed context.

Where factual evidence is required, the agent should still query/retrieve the actual source where appropriate.

Example:

Summary says:
"Earlier CUSTOMER_RISK contained exposure_amount."

If the user now asks for current metadata and the tool is available, retrieve metadata again rather than assuming the summary is definitive.

---

# 21. CONTEXT INVALIDATION

Consider when context may become stale.

Examples:

* Denodo metadata changed,
* document updated,
* previous query result was temporary,
* provider data changed.

Mark context according to type.

Do not keep raw tool results indefinitely as if they are permanent facts.

Object identity may be durable.

Provider results may need retrieval again.

Keep the initial invalidation policy simple and explicit.

# 26. PERFORMANCE

Avoid unnecessary repeated retrieval during one orchestration request.

If the same object metadata was just retrieved during the current request, reuse request-scoped evidence where safe.

Do not re-call a provider repeatedly for identical arguments within the same orchestration run unless there is a reason.

A request-scoped cache/deduplication mechanism is acceptable.

Do not introduce broad cross-user caching of sensitive data.

---

# 27. SECURITY

Context must respect user/provider access rules.

Do not allow:

* User A's conversation context into User B's request.
* User A's provider results into User B's context.
* restricted documents into the model context for unauthorised users.
* secrets/config files into project knowledge.
* access-control decisions to be made by the LLM.

ContextBuilder must only receive already-authorised source material or use provider access controls before retrieval.
