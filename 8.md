# STAGE 8 OBJECTIVE

Generalise and strengthen Vue Pilot's tool/data-source architecture so that **Denodo is the first provider, not the only provider**.

Vue Pilot should eventually be able to answer a question using multiple governed enterprise information sources.

Examples of future sources could include:

* Denodo metadata/data
* enterprise documentation
* application documentation
* data catalogue
* lineage service
* internal APIs
* project knowledge
* database metadata
* Git repositories
* ticketing/change systems
* approved search systems

Do NOT implement all these integrations in this stage.

The goal is to create the framework that allows additional sources to be added cleanly and safely.

A new provider should be introducible without modifying the central orchestrator in many places.

# 1. INSPECT EXISTING TOOL ARCHITECTURE

Before changing code:

1. Inspect Stage 6 orchestration interfaces.
2. Inspect Stage 7 Denodo provider.
3. Identify any Denodo-specific assumptions that leaked into generic orchestration code.
4. Refactor only where necessary.
5. Preserve working behaviour and tests.
6. Do not perform unnecessary architecture churn.

The resulting framework should make Denodo one implementation of a generic provider contract.

# 3. TOOL PROVIDER CONTRACT

Define/refine a clean provider contract.

Conceptually, a provider should be capable of:

* exposing provider identity,
* registering one or more tools,
* reporting availability/health where appropriate,
* executing its own registered operations through controlled adapters,
* returning normalised ToolResult objects,
* exposing configuration/policy metadata where needed.

Possible conceptual shape:

ToolProvider {
providerId
displayName

```
getTools(context)
isAvailable()
execute(toolName, input, context)
```

}

Do NOT blindly copy this interface if existing project conventions use another pattern.

Use the project's language and dependency injection standards.

---

# 4. TOOL DEFINITION MODEL

Strengthen the generic ToolDefinition model.

It should support concepts such as:

* globally unique tool ID/name
* provider ID
* human-readable description
* machine-readable input schema
* optional output schema/description
* operation category
* read-only/write capability
* sensitivity classification if useful
* permission requirements
* timeout policy
* cost/weight metadata if useful
* whether the tool may appear in model context

Do not add fields with no practical use.

Keep the model extensible but understandable.

---

# 5. UNIQUE TOOL NAMES

Avoid collisions when multiple providers expose similarly named operations.

Prefer namespaced or otherwise globally unique tool identifiers.

Examples conceptually:

denodo.search_views
denodo.get_view_metadata

future:

catalog.search_assets
docs.search_documents
lineage.get_lineage

Do not require the AI to understand internal implementation classes.

Expose stable semantic tool names.

---

# 6. TOOL REGISTRY

Create/refine a central ToolRegistry.

It should support operations such as:

* register provider
* register/discover provider tools
* find tool by ID
* list tools available to a request
* detect duplicate tool IDs
* filter tools according to policy/authentication
* route execution to the correct provider

Tool registration should preferably happen during startup/dependency configuration rather than inside request handling.

Avoid repeated reconstruction of static tool definitions for every user message unless necessary.

---

# 7. REQUEST-SPECIFIC TOOL AVAILABILITY

Not every tool should necessarily be available for every user/request.

Create a clean mechanism for resolving:

All registered tools
↓
user/session context
↓
application policy
↓
provider availability
↓
allowed tools for this request

The model should only receive tool definitions that it is actually allowed to request.

The AI should never be used as the access-control layer.

---

# 8. EXECUTION CONTEXT

Create/refine a typed ToolExecutionContext.

Potential fields may include:

* authenticated user identity/reference
* roles/permissions
* conversation ID
* correlation/request ID
* cancellation token/signal
* execution deadline
* relevant application context

Do not include credentials unless strictly needed by the provider, and do not expose secret context to the model.

The context belongs to deterministic execution code.

---

# 9. NORMALISED TOOL RESULT

Standardise ToolResult across all providers.

Conceptually:

ToolResult {
toolId
providerId
success
data
error
metadata
duration
}

Error information should support categories such as:

* invalid_input
* unauthorised
* forbidden
* not_found
* timeout
* unavailable
* provider_error
* result_too_large
* cancelled

Use an enum/discriminated union or equivalent where appropriate.

Do not make the orchestrator parse arbitrary exception messages.

---

# 10. PROVIDER ERROR BOUNDARY

A provider implementation should not be able to crash the entire orchestration pipeline through an uncaught provider-specific exception.

Introduce controlled provider execution boundaries.

Provider-specific exceptions should be converted to generic tool errors.

Log useful diagnostics server-side.

Return only appropriate information to the AI/user.

---

# 11. PROVIDER HEALTH / AVAILABILITY

Support the concept that a provider may be unavailable.

For example:

* Denodo MCP server unreachable.
* Documentation index unavailable.
* Catalogue service disabled in this environment.

The registry should be able to exclude unavailable tools or return a controlled unavailable result.

Do not allow provider outages to corrupt the entire registry.

Avoid running expensive live health checks before every tool call unless required.

Use sensible provider availability patterns.

---

# 12. CONFIGURATION-DRIVEN PROVIDERS

Providers should be configurable.

Allow concepts such as:

* enabled/disabled
* endpoint/configuration
* timeout
* limits
* feature flags

Use the existing application configuration model.

The application should support environments where:

Denodo = enabled

Future provider = disabled

without code changes.

Do not hard-code development hostnames, credentials or production endpoints.

---

# 13. TOOL POLICY LAYER

Introduce/refine a deterministic policy layer between tool selection and execution.

Conceptually:

Model requests tool
↓
Tool Registry resolves tool
↓
Policy evaluates request
↓
Input validated
↓
Provider executes

Policy may consider:

* authenticated user
* role
* provider
* operation type
* read/write classification
* configured limits
* environment
* request context

For Stage 8, create the architecture and basic policy behaviour.

Do not build an enormous enterprise entitlement engine unless one already exists.

---

# 14. TOOL INPUT VALIDATION

Every tool must validate model-generated input against the declared schema before execution.

Reject:

* missing required fields,
* malformed types,
* unexpected dangerous parameters,
* values outside configured limits.

Use schema validation already adopted by the project.

Do not trust tool arguments simply because they came from the LLM.

---

# 15. TOOL OUTPUT LIMITS

Create generic safeguards for provider results.

Potential controls:

* maximum payload bytes
* maximum item count
* truncation metadata
* timeout
* maximum text length

Individual providers may add stricter rules.

The common execution layer should protect the orchestration context from enormous results.

# 17. MULTI-PROVIDER REQUESTS

The framework must support one user question using multiple providers sequentially.

Ensure the Stage 8 abstraction does not assume every request belongs to exactly one provider.

# 21. ORCHESTRATOR CHANGES

Keep changes to the central Stage 6 orchestrator minimal.

The orchestrator should essentially:

1. obtain tools available to the request,
2. give tool definitions to the model,
3. receive requested tool call,
4. delegate execution to generic ToolExecutor/Registry,
5. receive ToolResult,
6. continue orchestration.

# 23. CONCURRENCY

Do not prematurely create aggressive parallel execution.

The orchestrator may occasionally benefit from independent tool calls in the future, but correctness is more important.

Ensure the contracts are asynchronous/non-blocking where appropriate so future parallel execution is possible.

For this stage, sequential execution is acceptable unless Stage 6 already supports parallel tool calls cleanly.
