You are continuing development of **Vue Pilot**, a conversational application intended to help authenticated users explore and understand Denodo data, metadata and related enterprise information.

The project already contains:

* Phase 1 — architecture, folder structure, technology choices and coding standards.
* Phase 2 — backend/API foundation.
* Phase 3 — authentication, users, roles and per-user session handling.
* Phase 4 — ChatGPT/Copilot-style chat UI with streamed responses and transient progress/activity display.
* Phase 5 — durable per-user conversations and message persistence.

Before writing code:

1. inspect all existing architecture,
2. understand the established AI/provider abstractions if any,
3. understand the chat streaming protocol,
4. understand the conversation persistence service,
5. inspect configuration conventions,
6. reuse existing dependency injection/service patterns,
7. do NOT introduce a competing architecture.

# PHASE 6 OBJECTIVE

Implement the **AI orchestration layer — the brain of Vue Pilot**.

Vue Pilot should NOT behave like:

User question
→
send everything directly to one LLM
→
return text.

Instead it should be capable of an agent-like workflow:

User question
↓
Understand the request
↓
Determine what information is required
↓
Determine which governed source/tool can provide that information
↓
Call that source/tool
↓
Inspect the result
↓
Decide whether enough information is available
↓
Potentially perform another tool call
↓
Synthesize the evidence
↓
Produce the final answer

The architecture must support Denodo/MCP initially while remaining extensible to additional enterprise information sources later.

Do not tightly couple the entire application to MCP.

MCP is one tool/source mechanism available to the orchestration layer.

---

# 1. CORE DESIGN PRINCIPLE

Separate:

## Reasoning / orchestration

from

## deterministic execution

The AI can decide that information is needed.

The AI should NOT receive unrestricted access to execute arbitrary operations.

Actual tool calls must pass through controlled application services/tool adapters with:

* explicit schemas,
* validation,
* authorization,
* timeouts,
* logging,
* error handling,
* configured limits.

Conceptually:

Chat Request
↓
Orchestrator
↓
Context Builder
↓
LLM / Agent
↓
Tool decision
↓
Tool Registry / Controlled Gateway
↓
Denodo MCP or another approved provider
↓
Structured result
↓
Orchestrator
↓
LLM synthesis
↓
Final Answer

Implement this separation cleanly.

---

# 2. DO NOT BUILD A GIANT AGENT CLASS

Break orchestration into focused services/interfaces.

The exact names should follow the repository conventions, but conceptually consider abstractions such as:

* ChatOrchestrator
* ContextBuilder
* ModelProvider / LlmClient
* ToolRegistry
* ToolExecutor
* ToolDefinition
* ToolResult
* ConversationContextService
* ProgressEventEmitter
* OrchestrationRequest
* OrchestrationResult
* Prompt/InstructionProvider

Do not treat these suggested names as mandatory.

The important requirement is separation of responsibilities.

---

# 3. ORCHESTRATION REQUEST

Create a typed request object representing what the orchestrator needs.

It may contain:

* authenticated user context,
* conversation ID,
* current user message,
* relevant previous conversation context,
* application/project context,
* request/correlation ID,
* cancellation information,
* available tool definitions,
* configuration.

Do not pass raw framework request objects deep into orchestration logic.

---

# 4. CONTEXT BUILDER

Implement a dedicated context-building layer.

It should assemble only relevant information needed for the current interaction.

Possible inputs:

* current question,
* recent conversation turns,
* application-level instructions,
* project/application knowledge,
* available tools,
* user authorization context where appropriate.

The context builder must be designed for future extension.

For example, later Vue Pilot may receive information from:

* Denodo MCP,
* application documentation,
* project Markdown knowledge,
* metadata catalogues,
* lineage services,
* governed databases,
* other approved APIs.

Do not hard-code all context into one enormous prompt string scattered across route handlers.

---

# 5. CONVERSATION CONTEXT

Use the persistence service created in Phase 5.

The orchestrator should be capable of understanding follow-up questions.

Example:

User:
"Show me the fields in CUSTOMER_RISK."

Assistant responds.

User:
"Which of those fields come from the source system?"

The second question should be processed with enough previous context to understand what "those fields" means.

However:

DO NOT send unlimited conversation history.

Implement configurable conversation context limits.

Prefer recent/relevant turns and leave architecture open for summarisation later.

---

# 6. MODEL PROVIDER ABSTRACTION

Use the AI/model technology already chosen/configured by the project.

Do not scatter direct model SDK calls across controllers and tool services.

Create/use a central provider abstraction.

The orchestration layer should depend on an application interface rather than a vendor-specific implementation wherever practical.

Configuration such as:

* deployment/model,
* endpoint,
* temperature,
* token limits,
* timeouts,

must come from the application's configuration/environment mechanism.

Do not hard-code credentials.

---

# 7. TOOL MODEL

Create a proper abstraction for tools.

Each tool should expose structured metadata such as:

* tool name
* description
* input schema
* output structure
* permission/policy information if applicable

The model should receive only tools available for the current request.

Do not give the model a generic function like:

execute_anything(command: string)

Tools must be explicit and narrow.

---

# 8. DENODO / MCP AS A TOOL PROVIDER

Integrate Denodo MCP behind a provider/adapter.

Do NOT make MCP the orchestration engine itself.

Conceptually:

Orchestrator
↓
ToolRegistry
↓
DenodoToolProvider
↓
MCP Client
↓
Configured Denodo MCP Server

This allows future providers such as documentation, lineage or catalogue services without redesigning the orchestrator.

---

# 9. DENODO CAPABILITIES

Where supported by the currently available Denodo MCP server/tools, prepare controlled operations around capabilities such as:

* discover schemas/databases,
* search/discover views,
* inspect view metadata,
* inspect columns/fields and data types,
* retrieve descriptions,
* inspect relationships,
* inspect lineage/dependencies,
* validate query/VQL where supported,
* execute approved read-only queries where supported.

IMPORTANT:

Do not invent MCP tools that do not exist.

Inspect the actual MCP capability/tool definitions available in the project/environment and create adapters around what really exists.

---

# 10. METADATA-FIRST BEHAVIOUR

For data-related questions, prefer a metadata-first process.

Example:

User:
"What was customer exposure for X?"

Do NOT immediately fabricate SQL/VQL based only on the user's wording.

The orchestrator should be able to:

1. identify likely relevant views,
2. inspect their schemas/metadata,
3. identify appropriate fields,
4. understand relationships where necessary,
5. construct a query using known metadata,
6. validate it if a validation capability exists,
7. execute only through an approved read-only path,
8. analyse the returned information,
9. answer the question.

This is an important design principle for reliability.

---

# 11. ITERATIVE TOOL LOOP

Implement a bounded orchestration loop.

Conceptually:

MAX_STEPS = configurable safe limit

for each step:

```
ask model for next action

if final answer:
    return answer

if tool call:
    validate tool request
    execute approved tool
    return structured result to model

otherwise:
    handle invalid response
```

Stop if limits are exceeded.

Do NOT create an unbounded recursive agent.

Define configurable limits such as:

* maximum tool calls,
* maximum orchestration steps,
* execution timeout,
* response size,
* context/token budget where available.

---

# 12. STRUCTURED TOOL RESULTS

Tool results should be returned to the orchestrator in a structured format.

Conceptually:

ToolResult {
toolName
success
data
error
metadata
duration
}

Avoid passing uncontrolled exception strings directly to the LLM.

The orchestrator should distinguish:

* successful empty result,
* permission denied,
* validation failure,
* timeout,
* provider unavailable,
* execution error.

---

# 13. USER-FRIENDLY ACTIVITY STREAMING

Integrate with Phase 4's transient activity display.

During processing, emit USER-FRIENDLY operational events.

Examples:

* Understanding your question...
* Finding relevant Denodo views...
* Inspecting CUSTOMER_RISK metadata...
* Checking available fields...
* Retrieving authorised data...
* Analysing the results...
* Preparing the answer...

Do not expose:

* hidden chain-of-thought,
* model scratchpad,
* confidential system prompts,
* raw internal reasoning.

The user should understand what type of work is happening without seeing private model reasoning.

Once the final response is ready:

* stream/render the final answer,
* end the progress state,
* do not persist operational progress events as ordinary chat messages.

---

# 14. FINAL RESPONSE SYNTHESIS

The model should synthesize a coherent response based on retrieved evidence.

The answer should distinguish between:

* information discovered from metadata,
* information obtained from data/tool execution,
* explanation/inference generated by the AI.

Do not fabricate object names, columns or query results.

If required information could not be obtained, say so clearly instead of inventing an answer.

---

# 15. HANDLING NON-DENODO QUESTIONS

Not every question requires a Denodo tool.

Example:

"What is the difference between a Denodo base view and derived view?"

The orchestrator may be able to answer using available knowledge/context without querying Denodo.

The orchestration system must therefore decide whether a tool is necessary.

Do not force an MCP call for every question.

---

# 16. HANDLING FOLLOW-UP QUESTIONS

Support contextual follow-ups such as:

User:
"Find views containing trade exposure."

Then:
"Show the columns of the second one."

Then:
"Which columns are monetary values?"

The orchestrator must use conversation context plus tool results appropriately.

Do not rely exclusively on the raw latest message.

---

# 17. AUTHORIZATION

The authenticated user context from Phase 3 must remain part of governed execution.

Tool calls must not allow users to bypass access controls.

The orchestration layer must not grant additional access simply because the model requested an object.

Never trust model output as authorization.

Think:

model proposes action
↓
application validates action
↓
authorized tool executes action

rather than:

model asks → execute blindly.

---

# 18. READ-ONLY SAFETY

At this phase Vue Pilot should primarily operate as an information/exploration assistant.

Do not introduce unrestricted destructive capabilities.

Do NOT permit:

* arbitrary operating-system shell execution,
* unrestricted SQL/VQL writes,
* DROP operations,
* DELETE/UPDATE/INSERT through generic AI-generated commands,
* production administrative operations,
* arbitrary external HTTP access.

If an existing Denodo capability can alter state, do not expose it to the agent merely because it exists.

Start with approved read-only operations.

---

# 19. PROMPT / INSTRUCTION MANAGEMENT

Do not place a massive system prompt directly inside route/controller code.

Create a clean prompt/instruction management mechanism.

Separate concepts such as:

* core Vue Pilot behaviour,
* Denodo-specific guidance,
* tool-use instructions,
* response formatting guidance.

Store them according to existing project conventions.

Keep prompt changes reviewable.

---

# 20. RESPONSE QUALITY RULES

Instruct/configure the agent to:

* use available tools when factual metadata is required,
* not invent schemas/views/columns,
* inspect metadata before constructing queries,
* ask for clarification only when genuinely necessary,
* use existing conversation context,
* make bounded tool calls,
* explain failures clearly,
* avoid claiming actions it did not perform,
* produce readable responses,
* use Markdown appropriately,
* display SQL/VQL in fenced code blocks when useful.

---

# 21. OBSERVABILITY

Create useful structured logging.

Each orchestration run should have a request/correlation ID.

Capture operational metadata such as:

* request started,
* orchestration steps,
* tool called,
* tool duration,
* success/failure,
* model/provider duration,
* total request duration.

Do NOT routinely log:

* credentials,
* access tokens,
* full secret values,
* unnecessary sensitive query results,
* hidden AI reasoning.

Design logging so debugging is possible without compromising enterprise data.

---

# 22. ERROR HANDLING

Handle failures at each boundary.

Examples:

## LLM unavailable

Return a user-friendly failure.

## MCP unavailable

The orchestrator should recognise the tool provider failure and respond appropriately.

## Tool timeout

Terminate safely.

## Invalid tool arguments

Reject before execution.

## Unknown tool

Do not execute.

## Maximum steps reached

Stop cleanly rather than looping forever.

## Partial evidence available

Answer only what can be supported and explain the limitation.

---

# 23. CANCELLATION

Where supported by the existing Phase 4 request model, propagate cancellation.

If the user presses Stop:

* stop additional orchestration work where possible,
* cancel outstanding provider requests where supported,
* do not initiate new tool calls,
* leave conversation state consistent.

---

# 24. PERSISTENCE INTEGRATION

Use Phase 5 persistence.

The durable flow should conceptually be:

User message
→ persist
→ orchestrate
→ stream progress/final output
→ persist final assistant message

Do not save every temporary model/tool event as a normal message.

Store only durable information required by the application.

If useful for audit/debugging, operational execution records should be modelled separately from user-visible conversation history.

---

# 25. EXTENSIBILITY FOR FUTURE SOURCES

Design the system so a future capability can be added approximately like:

registerToolProvider(new LineageToolProvider())

rather than rewriting the orchestration engine.

Possible future sources may include:

* metadata catalogue,
* enterprise documentation,
* lineage API,
* governed database services,
* project knowledge,
* application-specific APIs.

Do NOT implement all of these now.

Simply ensure the architecture does not make Denodo MCP the only possible information source.

---

# 26. DO NOT ADD LANGCHAIN JUST BECAUSE THIS IS AGENTIC

Do not introduce an orchestration framework solely because it is fashionable.

First inspect the architecture and dependencies already chosen in Phase 1.

If an agent/orchestration framework has already been intentionally selected by the project, use it according to that architecture.

Otherwise build the minimum clean orchestration abstractions required using the existing model SDK/provider.

Avoid adding a large dependency when the required loop can be implemented cleanly with existing technology.

---

# 27. TESTING STRATEGY

The orchestration layer must be testable without calling real external services on every test.

Use interfaces/fakes/mocks for:

* model provider,
* MCP provider,
* tool executor,
* conversation context.

Add unit tests for scenarios such as:

Model determines no tool required.

Final answer returned.

### Scenario B — one tool

Model requests metadata tool.

### Scenario C — multiple tools

### Scenario D — tool failure

### Scenario E — invalid tool request

### Scenario F — max-step protection

Model repeatedly requests tools.

Verify the configured maximum terminates processing.

### Scenario G — follow-up question

Previous conversation contains the referenced view/object.

Verify relevant context is passed.

### Scenario H — cross-user security

Ensure orchestration never retrieves another user's conversation context.

# 30. DEFINITION OF DONE

Phase 6 is complete when:

1. Chat requests flow through an orchestration service.
2. The orchestrator understands current and relevant prior conversation context.
3. The model can decide whether a tool is required.
4. Approved tools can be discovered through a registry/provider abstraction.
5. Denodo MCP is integrated behind a controlled adapter/provider.
6. Tool execution is validated before execution.
7. Multiple sequential tool calls are supported.
8. Tool loops are bounded.
9. Metadata-first behaviour is supported.
10. User-friendly progress events appear in the Phase 4 UI.
11. Hidden reasoning is never shown.
12. The final answer streams back to the user.
13. Final assistant responses are persisted through Phase 5.
14. Authentication and authorization remain enforced.
15. Read-only safety restrictions are maintained.
16. Additional tool providers can be introduced later without rewriting the orchestrator.
17. Error and cancellation behaviour is controlled.
18. Observability/logging exists.
19. Unit and integration tests cover the important flows.
20. Existing phases remain functional.
