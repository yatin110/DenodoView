You are continuing development of **Vue Pilot**.

The repository should now contain:

* Phase 1 — project architecture and standards.
* Phase 2 — backend/API foundation.
* Phase 3 — authentication, users, roles and per-user session handling.
* Phase 4 — ChatGPT/Copilot-style conversational UI with streaming-ready messages and conversation sidebar.

Before modifying anything, inspect the current implementation carefully.

Do not redesign functionality that already works.

# PHASE 5 OBJECTIVE

Implement durable **per-user conversation and message persistence**.

A logged-in Vue Pilot user must be able to:

* start a new conversation,
* ask multiple questions within it,
* leave the application,
* return later,
* see their previous conversations,
* reopen a conversation,
* continue where they left off.

Conversation ownership must be enforced on the backend.

A user must never be able to retrieve another user's conversations simply by manipulating a conversation ID.

This phase is about persistence and conversation lifecycle.

The AI reasoning/orchestration engine remains Phase 6.

---

# 1. REVIEW EXISTING STORAGE

First inspect the persistence/database approach already selected during earlier phases.

Use that existing approach.

Do NOT add a second database technology simply for conversation history.

Use migrations/schema-management conventions already established in the repository.

---

# 2. DATA MODEL

Create a clean persistent model for conversations and messages.

At minimum the conceptual model should support:

## Conversation

* unique conversation ID
* owner/user ID
* title
* created timestamp
* updated timestamp
* optional last-message timestamp
* status if useful
* metadata field only if justified

## Message

* unique message ID
* conversation ID
* role
* content
* created timestamp
* ordering/sequence information if required
* optional metadata
* optional status/error information where appropriate

Use robust server-generated identifiers.

Do not use UI array indexes as permanent identifiers.

Create proper foreign-key relationships/indexes according to the database technology already in use.

---

# 3. USER OWNERSHIP

This is critical.

Every conversation must belong to the authenticated user.

The backend must derive the user identity from the authenticated request/session established in Phase 3.

DO NOT trust a user ID supplied by the frontend for ownership decisions.

For every read/update/delete operation:

authenticated user
+
requested conversation
→
verify ownership
→
perform operation

A conversation belonging to another user should not be accessible.

Choose appropriate 404/403 behaviour consistent with existing security conventions.

---

# 4. CONVERSATION CREATION

Implement conversation creation.

When the user starts a new chat, avoid unnecessarily creating large numbers of empty database conversations.

Prefer one of these sensible approaches according to existing application architecture:

* create the conversation when the first user message is submitted,

or

* create it when New Chat is explicitly initiated but clean up/avoid empty abandoned conversations.

Keep the behaviour predictable.

---

# 5. MESSAGE PERSISTENCE

When the user sends a message:

1. validate authenticated user,
2. validate/create conversation,
3. persist the user message,
4. allow the existing response mechanism to operate,
5. persist the completed assistant message,
6. update conversation timestamps.

The design must be ready for Phase 6, where the assistant response will be generated by the orchestration engine.

Do not duplicate streaming chunks as separate persisted messages.

The canonical assistant message should represent the final assembled answer.

Transient progress/activity events should NOT normally become conversation messages.

---

# 6. CONVERSATION HISTORY API

Implement appropriate API endpoints/services for:

* create conversation,
* list current user's conversations,
* retrieve one conversation with messages,
* update conversation title if supported,
* delete/archive conversation,
* append/read messages.

Follow the REST/API conventions already established in the project.

Do not create APIs that accept arbitrary `userId` values for normal user conversation access.

The authenticated identity determines the user.

---

# 7. LISTING CONVERSATIONS

The conversation sidebar from Phase 4 should now use persisted backend data.

Conversation list requirements:

* current authenticated user's conversations only,
* newest/recently updated conversations first,
* display conversation title,
* appropriate loading state,
* appropriate empty state,
* select conversation,
* restore messages when selected.

Avoid retrieving the complete message content for every conversation simply to populate the sidebar.

Use lightweight conversation summaries.

---

# 8. CONVERSATION TITLES

Implement a simple title strategy.

For now, an acceptable approach is deriving the title from the first user question, truncated to a sensible length.

Do NOT introduce another expensive AI call solely to generate titles unless the architecture already provides one and it is explicitly justified.

Keep title generation replaceable so AI-generated titles can be introduced later if desired.

---

# 9. CONTINUING A CONVERSATION

When an existing conversation is opened:

1. retrieve persisted messages,
2. render them in chronological order,
3. restore the conversation ID into application state,
4. allow another user message to be submitted,
5. append subsequent messages to the same conversation.

The interface should feel continuous.

---

# 10. PAGINATION / SCALE

Design for conversation history to grow.

Do not assume a user will only have 10 conversations.

Implement sensible pagination, cursor-based retrieval, or another approach consistent with the backend standards already used.

Similarly, avoid architecture that requires loading thousands of messages unnecessarily.

For normal initial implementation, loading the messages of the selected conversation is acceptable, but the service/API design should not make future pagination impossible.

---

# 11. DELETE OR ARCHIVE

Provide a way for the user to remove a conversation from their history.

Use the application's existing design conventions.

If soft-delete/archive is already an architectural pattern, use it.

Otherwise do not over-engineer.

The server must enforce ownership before deletion.

The UI should prevent accidental deletion using an appropriate confirmation interaction.

---

# 12. SESSION VS CONVERSATION

Do not confuse:

* authenticated login session
  with
* Vue Pilot conversation.

A user may have many conversations during the same login session and reopen conversations created during previous login sessions.

Ensure naming throughout the code makes this distinction clear.

---

# 13. TRANSIENT EVENTS

Do NOT persist temporary processing messages such as:

* Searching metadata...
* Inspecting schema...
* Running query...
* Analysing results...

These are request-level progress/activity events.

Only persist information that belongs in durable conversation history.

The expected durable history is primarily:

User:
"Which customer views contain credit risk?"

Assistant:
final response

rather than every internal operation performed to generate the answer.
