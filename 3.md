Continue development of Vue Pilot.

This is implementation stage 3.

The purpose of this stage is to introduce:

- authentication architecture
- user identity
- user persistence
- roles
- authorization
- secure per-user request context
- login/session handling

This foundation will later be used to ensure that every Vue Pilot conversation and message belongs to the correct user.

============================================================
APPLICATION CONTEXT
============================================================

Vue Pilot is a multi-user enterprise conversational AI application.

Eventually many users may use the application.

Each user will have their own:

- conversations
- messages
- conversation history
- preferences
- possibly favourite/saved conversations
- possibly user-specific tool permissions

It is CRITICAL that one user cannot retrieve or manipulate another user's data.

Future persistence will therefore follow ownership rules such as:

User
  |
  +---- Conversations
            |
            +---- Messages

All future queries for user-owned resources must enforce ownership on the server.

Never rely on the frontend to enforce this.

============================================================
AUTHENTICATION STRATEGY
============================================================

The application should support enterprise authentication without tightly coupling the entire application to one identity provider.

Design an authentication abstraction.

The expected production authentication model is OIDC / OAuth2 based.

Microsoft Entra ID / Azure AD is a likely production provider.

However, do not make core application logic dependent specifically on Microsoft libraries.

Create an architecture that can support providers such as:

- Microsoft Entra ID
- another OIDC provider
- local development authentication

The application should have an internal User identity regardless of external identity provider.

============================================================
IDENTITY MODEL
============================================================

Create a User database model.

Use an internal UUID primary key.

Suggested fields:

id
external_subject
issuer
email
display_name
is_active
created_at
updated_at
last_login_at

Consider appropriate nullable/required fields.

The important concept is:

The external identity should be uniquely identified by something equivalent to:

issuer + subject

Do NOT rely solely on email address as the immutable identity key.

Email addresses can change.

Create an appropriate unique database constraint.

Do not store external access tokens in the User table.

============================================================
ROLE MODEL
============================================================

Introduce basic role-based access control.

Initially support:

USER
ADMIN

Design it so additional roles can be introduced later without redesigning the application.

For example future roles might include:

DATA_STEWARD
SUPPORT
POWER_USER

but DO NOT add them now unless there is a reason.

Choose a simple role implementation.

Either:

- a role column/enum if one role per user is enough initially

OR

- user-role association if the existing architecture clearly benefits from multiple roles.

Do not over-engineer RBAC.

Document your choice.

============================================================
AUTHENTICATION PROVIDER ABSTRACTION
============================================================

Create a backend abstraction for authentication.

For example, concepts might include:

AuthenticatedPrincipal

containing:

subject
issuer
email
display_name
claims

and an authentication provider/service responsible for validating identity.

Core application services should depend on an authenticated application User, not raw JWT claims.

Keep provider-specific JWT/OIDC logic isolated from domain services.

============================================================
PRODUCTION AUTHENTICATION
============================================================

Prepare the backend for OIDC/JWT authentication.

Configuration should support concepts such as:

AUTH_PROVIDER
OIDC_ISSUER
OIDC_AUDIENCE
OIDC_CLIENT_ID

and other values where appropriate.

Do NOT hard-code tenant IDs, client IDs, secrets, URLs, or certificates.

JWT validation must eventually correctly validate at minimum:

- signature
- issuer
- audience
- expiration

Do not merely decode JWT payloads without validating them.

If production OIDC cannot be fully exercised locally because provider details are unavailable, implement the provider cleanly and cover its logic with unit tests/mocks where possible.

Do not fabricate real tenant details.

============================================================
LOCAL DEVELOPMENT AUTHENTICATION
============================================================

Developers need to run Vue Pilot without requiring a production identity provider.

Implement a safe DEVELOPMENT-ONLY authentication mechanism.

For example:

AUTH_PROVIDER=dev

could allow a configured development user.

Possible configuration:

DEV_AUTH_USER_EMAIL
DEV_AUTH_USER_NAME

The backend can create/resolve a development principal.

IMPORTANT:

Development authentication must NEVER silently activate in production.

Add a hard safeguard such as:

If APP_ENV is production and AUTH_PROVIDER is dev:
    fail application startup.

Document this clearly.

Do not create an unauthenticated "admin by default" production path.

============================================================
USER PROVISIONING
============================================================

When a valid external principal authenticates:

1. Read the validated subject and issuer.
2. Look for an existing User using issuer + subject.
3. If none exists, create the internal User.
4. Update appropriate mutable information such as:
   - display name
   - email
   - last_login_at
5. Return/use the internal application User.

Keep this logic in a service such as:

UserService
or
AuthenticationService

rather than inside every route.

Avoid creating a user repeatedly for every request.

============================================================
CURRENT USER DEPENDENCY
============================================================

Implement a FastAPI dependency similar conceptually to:

get_current_user()

Routes that require authentication can use:

current_user = Depends(get_current_user)

The dependency should return the INTERNAL User object or a clearly defined application-user representation.

Individual routes should not repeatedly parse authentication tokens.

Also create authorization helpers such as:

require_role(...)

if appropriate.

============================================================
AUTHENTICATION API
============================================================

Create endpoints appropriate to the selected architecture.

At minimum provide something similar to:

GET /api/v1/auth/me

Response example:

{
  "id": "...",
  "email": "...",
  "display_name": "...",
  "roles": ["USER"]
}

This endpoint must require authentication.

Potentially provide an auth/config endpoint if the frontend needs information about the configured provider.

Do not expose:

- provider secrets
- tokens
- signing keys
- confidential claims

============================================================
FRONTEND AUTHENTICATION FOUNDATION
============================================================

Update the React frontend to understand authentication.

Create a clean auth feature/module.

Conceptually include things such as:

AuthContext / AuthProvider
useAuth()
CurrentUser type
protected routes
loading state
authenticated state
unauthenticated state

Do not scatter auth logic throughout components.

The frontend should be able to:

1. determine whether a user is authenticated
2. retrieve the current user
3. expose current user information to components
4. show an appropriate login/authentication state
5. protect application routes

For development mode, integrate cleanly with the development authentication mechanism.

For production OIDC, build the integration in a provider-aware way based on the selected architecture.

Do not hard-code production identity information.

============================================================
SESSION HANDLING
============================================================

Be precise about terminology.

Vue Pilot will eventually contain two different concepts:

1. Authentication/login session
2. Chat conversation session

This task concerns AUTHENTICATION/login session only.

Chat conversations will be implemented separately later.

Choose a secure session/token handling strategy suitable for the frontend/backend architecture.

Avoid storing long-lived sensitive tokens in localStorage if a safer architecture is practical.

If using cookies:

- use HttpOnly where appropriate
- use Secure in production
- use SameSite appropriately
- consider CSRF implications

If using bearer tokens:

- document where tokens live
- document how refresh/expiry works
- avoid logging them

Do not invent a complex refresh-token service unless required by the chosen provider architecture.

============================================================
USER OWNERSHIP FOUNDATION
============================================================

The most important future requirement is ownership.

Create a clear convention for future repository/service methods.

BAD FUTURE PATTERN:

get_conversation(conversation_id)

followed by assuming access is allowed.

PREFERRED FUTURE PATTERN:

get_conversation_for_user(
    conversation_id,
    user_id
)

or equivalent authorization enforcement.

Document this in the architecture.

Future resources such as:

Conversation
Message
SavedPrompt
UserPreference

must always be accessed relative to the authenticated user's identity unless explicitly authorized otherwise.

Do NOT implement Conversation or Message persistence yet.

============================================================
AUTHORIZATION
============================================================

Implement enough RBAC to demonstrate server-side authorization.

For example create a protected endpoint such as:

GET /api/v1/users/me

or use /auth/me.

If an admin-only endpoint is useful for validating RBAC, keep it minimal and non-sensitive.

For example:

GET /api/v1/admin/health

could verify ADMIN authorization.

Do not build an admin management UI yet.

Expected behaviour:

Unauthenticated:
401

Authenticated but insufficient role:
403

Authorized:
200

Ensure the application clearly distinguishes authentication and authorization errors.

Enhance request logging so authenticated requests can be correlated with an internal user ID where appropriate.

============================================================
SECURITY REQUIREMENTS
============================================================

Ensure:

- passwords are not needed for OIDC authentication
- tokens are not persisted unnecessarily
- JWT validation is real, not just decoding
- development auth cannot operate in production
- user role is determined server-side
- frontend role checks are not considered security controls
- disabled users cannot access protected APIs
- error messages do not expose sensitive authentication internals

If is_active is false:

Return an appropriate authorization response.

============================================================
DATABASE INDEXES
============================================================

Add sensible indexes/constraints for user lookup.

At minimum ensure efficient/unique lookup using:

issuer

Do not add unnecessary indexes.
