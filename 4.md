# PHASE 4 OBJECTIVE

Implement the primary **Vue Pilot conversational user interface**.

The experience should feel closer to **ChatGPT / GitHub Copilot Chat** than a conventional enterprise form application.

Vue Pilot will eventually allow users to ask questions about Denodo data, metadata, schemas, views, lineage and business/technical information.

The AI orchestration itself will be implemented in Phase 6.

Conversation persistence will be implemented in Phase 5.

Therefore, this phase must focus on creating a strong, reusable conversational UI and frontend/backend streaming contract without prematurely implementing the AI reasoning engine or database persistence.

# 3. WELCOME / EMPTY STATE

When a new conversation contains no messages, show an attractive Vue Pilot welcome state.

Example concept:

"How can I help you explore Denodo?"

Provide several example prompts such as:

* Find the customer-related views available to me.
* Explain what this Denodo view contains.
* Show the lineage for a particular field.
* Which views contain customer risk information?
* Help me build a query for a particular dataset.

Design the examples as clickable prompt suggestions that populate or submit the chat input.

Do not hard-code the architecture around these exact questions.

Create a polished chat composer at the bottom of the application.

Requirements:

* Multi-line input.
* Enter submits.
* Shift+Enter inserts a new line.

Structure the component so additional capabilities can later be added, for example:

* attachments,

# 5. MESSAGE MODEL

Define proper frontend types/interfaces for conversation messages.

At minimum consider:

* messageId
* conversationId
* role: user | assistant | system where appropriate
* content
* createdAt
* status

Do not tightly couple the UI components to raw HTTP response objects.

Use application/domain types.

Prepare types so Phase 5 can introduce persisted message IDs without major changes.

---

# 6. STREAMING RESPONSE EXPERIENCE

The application must be designed for streamed assistant responses.

When a user sends a message:

1. Immediately display the user's message.
2. Create an assistant response placeholder.
3. Show an appropriate working indicator.
4. Receive response chunks/events from the backend.
5. Incrementally append content to the assistant message.
6. Render the final completed assistant response.
7. Recover cleanly from errors.

Use the streaming mechanism compatible with the architecture already established in the project.

Do not implement a fake character-by-character typing animation when actual streaming chunks are available.

Streaming code must be isolated behind an API/service layer rather than embedded directly throughout UI components.

---

# 7. ACTIVITY / PROGRESS DISPLAY CONTRACT

Phase 6 will eventually perform multiple steps such as:

* understanding the request,
* finding metadata,
* inspecting schemas,
* querying a governed data source,
* analysing results,
* composing the response.

Prepare the frontend for receiving temporary activity events.

Examples of USER-FRIENDLY activity text:

* Understanding your question...
* Looking for relevant views...
* Inspecting metadata...
* Checking available fields...
* Retrieving information...
* Analysing results...
* Preparing the answer...

IMPORTANT:

These are operational progress messages, NOT the model's private chain-of-thought.

Never design the application to display hidden AI reasoning or internal chain-of-thought.

Create an activity/progress component capable of displaying these transient events while a response is being generated.

Once the final answer is complete, the activity area should collapse, disappear or become unobtrusive.

The final conversation history should primarily contain the user question and final assistant answer.
