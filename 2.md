============================================================
APPLICATION CONTEXT
============================================================

Vue Pilot is an enterprise conversational AI application.

Initially its primary domain will be Denodo.

Eventually a user will ask questions such as:

- Find views related to counterparty information.
- Explain a Denodo view.
- Show dependencies for a view.
- Find metadata for a field.
- Identify which source contains particular information.
- Analyse metadata or query results.

The application will eventually contain an AI orchestration layer capable of calling different tools and data sources.

Potential future sources include:

- Denodo via MCP
- Denodo APIs
- internal databases
- documentation repositories
- other MCP services
- enterprise APIs

The backend therefore needs to support:

- normal REST APIs
- future streaming AI responses
- authentication
- persistent conversations
- asynchronous external calls
- tool integrations
- structured errors
- auditing/observability

Do NOT implement those future capabilities fully in this stage.

This stage establishes the backend on which they will be built.

============================================================
OBJECTIVE
============================================================

Create a production-quality FastAPI backend foundation with:

- application lifecycle management
- API versioning
- health endpoints
- configuration
- database infrastructure
- request IDs
- structured logging
- consistent errors
- dependency injection
- repository/service boundaries
- future streaming readiness
- automated tests

Keep the design practical and understandable.

Do not introduce a large framework on top of FastAPI.

============================================================
1. APPLICATION FACTORY / STARTUP
============================================================

Review the existing app/main.py.

Structure application startup cleanly.

Prefer a create_app() style factory if it improves testing.

The application should:

- obtain settings from the centralized configuration
- configure logging
- register middleware
- register exception handlers
- register API routers
- support FastAPI lifespan startup/shutdown handling
- expose OpenAPI docs appropriately depending on environment

Avoid expensive external connections during module import.

============================================================
2. API STRUCTURE
============================================================

Use versioned endpoints beneath:

/api/v1

Create an API router structure that will support future features such as:

/api/v1/auth
/api/v1/users
/api/v1/conversations
/api/v1/chat
/api/v1/tools
/api/v1/sources

Do NOT implement these feature APIs yet unless a minimal placeholder/interface is needed.

Implement foundation endpoints such as:

GET /api/v1/health

Return something similar to:

{
  "status": "ok",
  "service": "vue-pilot",
  "version": "...",
  "environment": "..."
}

Also create a readiness endpoint such as:

GET /api/v1/ready

It should be structured so that future checks can include:

- database
- tool services
- MCP services

At this stage it can check the application/database only if appropriate.

Do not leak credentials or sensitive configuration through health endpoints.

============================================================
3. STANDARD API RESPONSE / ERROR MODEL
============================================================

Create a consistent error format.

For example:

{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "The requested resource was not found.",
    "request_id": "..."
  }
}

The exact implementation can differ if there is a good reason.

Create appropriate domain/application exceptions, for example:

- AppException
- ResourceNotFoundError
- UnauthorizedError
- ForbiddenError
- ConflictError
- ExternalServiceError

Map these centrally to HTTP responses.

Validation failures should also be returned consistently where practical.

Unexpected failures:

- should be logged
- should include request ID in logs
- must not expose Python stack traces or secrets to clients

============================================================
4. REQUEST CORRELATION ID
============================================================

Add request correlation/request IDs.

For every request:

- accept an existing X-Request-ID if reasonable
OR
- generate a UUID

Return it in the response header.

Make the request ID available to application logging.

This will later be important when tracing:

User request
-> API
-> agent
-> tool invocation
-> Denodo
-> response

Do not introduce unsafe global mutable request state.

Use an appropriate context-local mechanism if needed.

============================================================
5. LOGGING
============================================================

Create structured backend logging.

At minimum logs should make it easy to determine:

- timestamp
- log level
- logger/module
- message
- request ID

Prepare the design so future logs can include fields such as:

- user ID
- conversation ID
- tool name
- duration
- outcome

Do NOT log:

- bearer tokens
- passwords
- secrets
- database passwords
- full sensitive prompts by default

If HTTP request logging is added, be careful not to dump confidential request bodies.

============================================================
6. DATABASE FOUNDATION
============================================================

Complete the database infrastructure started in stage 1.

Use:

- SQLAlchemy 2.x
- modern declarative models
- Alembic
- configuration-driven DATABASE_URL

Development should work with SQLite.

Production should be able to use PostgreSQL later without architectural changes.

Create:

- engine management
- session factory
- FastAPI database dependency
- declarative Base
- migration infrastructure

Use sensible transaction boundaries.

Do not create authentication/user/conversation tables yet unless required for database smoke testing.

If you need a simple technical model for validating migrations, avoid introducing fake domain tables unnecessarily.

============================================================
7. SERVICE AND REPOSITORY PATTERN
============================================================

Establish lightweight conventions for services and repositories.

Example future request:

API route
    -> ConversationService
        -> ConversationRepository
            -> database

or:

API route
    -> AgentService
        -> ToolRegistry
            -> DenodoTool

Do not create interfaces for every class purely for abstraction.

Use abstractions where they provide real value, particularly around:

- database access
- external services
- AI providers
- tools

Write a short developer note explaining the intended pattern.

============================================================
8. DEPENDENCY INJECTION
============================================================

Use FastAPI dependency injection appropriately.

Prepare clean dependencies for things such as:

- settings
- database session
- current user (to be implemented next)
- future services

Avoid global service singletons where this would make testing difficult.

Expensive shared clients may eventually be lifecycle-managed, so architect for that possibility.

============================================================
9. CORS
============================================================

Configure CORS using environment configuration.

Do not use:

allow_origins=["*"]

together with credentials.

Use FRONTEND_ORIGIN or equivalent configuration.

Development defaults can allow the local frontend development URL.

============================================================
10. STREAMING READINESS
============================================================

Vue Pilot will later stream AI progress/results to the browser.

The likely flow will eventually look like:

POST user message

Backend emits events such as:

conversation_started
thinking
tool_started
tool_completed
response_delta
response_completed
error

Do NOT implement the AI stream now.

However:

- assess whether Server-Sent Events is appropriate
- make sure middleware/API architecture will not prevent streaming
- create documentation describing the expected future streaming approach

Prefer SSE for one-directional server-to-browser AI response streaming unless there is a strong architectural reason to use WebSockets.

Document the decision in docs/architecture.md.

============================================================
11. FUTURE TOOL ARCHITECTURE
============================================================

Create only the minimal contracts necessary to make future tool integration clean.

A future tool may have concepts similar to:

ToolDefinition:
- name
- description
- input schema

Tool:
- metadata/definition
- execute(...)

ToolResult:
- success
- output
- metadata
- source/evidence references
- error information where applicable

The eventual orchestrator should not know how Denodo itself works.

It should interact with tools through a common contract.

DO NOT implement Denodo or MCP calls yet.

Avoid building a complicated agent framework.

Simple Python protocols/ABCs/types are enough if appropriate.
